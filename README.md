# Detection Improvement Tool (prototype)

A guided, browser-based tool for improving KQL detection rules. You paste a rule, upload a schema and a sample of each table it uses, and the tool assesses the rule against the L1/L2/L3 maturity decision tree, then rewrites it with improvements you can switch on and off. Every change is coloured and lettered by the improvement it belongs to, and checked against the reference data you uploaded.

| Letter | Improvement | Status in this build |
| --- | --- | --- |
| E | Entity enrichment (A1, IdentityInfo lookup) | Working |
| T | Threat intelligence correlation (A3) | Working |
| H | Evasion hardening (parameter abbreviations, carets, quotes, string concatenation) | Working |
| B | Baseline deviation | Planned |
| N | ASIM normalisation (A6) | Applicability shown, rewrite planned |

KQL for Microsoft Sentinel and Defender XDR Advanced Hunting only, for now.

## How it handles data

Everything runs in the browser. Reference files are read into memory and are never uploaded, saved or committed, and they are cleared when the page is closed or reloaded. The site is static, so GitHub Pages only serves the code. Use lab data where you can, and mask client data before exporting it.

The `local-cases/` folder is ignored by git, so it is a safe place to keep your own test cases on your machine.

## Running it

```bash
npm ci
npm run dev      # local development server
npm test         # engine unit tests
npm run build    # type check and production build into dist/
```

The worked example (button on the first step) uses synthetic data from `src/examples/encoded-powershell/`, generated by `npm run fixtures`.

## Deployment

`.github/workflows/deploy.yml` tests, builds and publishes to GitHub Pages on every push to `main`. In the repository settings, set **Pages > Build and deployment > Source** to **GitHub Actions**. `.github/workflows/ci.yml` runs the tests and build on pull requests.

## How the improvements are generated

The engine is rules-based and deterministic. It does not call an AI service. Each improvement fills a reviewed template using only column names found in your uploaded schemas, and every column it writes is checked against those schemas before the output is shown.

- **Entity enrichment** picks the strongest account identifier shared by the base table and IdentityInfo (object IDs and SIDs before UPNs and names), and raises a soundness warning if only a weak identifier is available. It uses `lookup kind=leftouter` with the most recent IdentityInfo record from the last 14 days, and renames any column that would collide with the base table.
- **Threat intelligence** picks the observable to check (hash, IP address, domain or URL), preferring columns the rule already uses and, for built-in Windows binaries, the initiating process hash. ObservableKey values are taken from your indicator sample where present and flagged as assumed where not. Only active, unexpired indicators are used, compared in lower case.
- **Evasion hardening** finds command-line conditions, identifies the executable from the rule's image name filter, and replaces literal parameter matches with a pattern covering every accepted prefix form and documented alias, with hyphen, forward slash or Unicode dash prefixes. Matching runs against a cleaned copy of the command line with carets, double quotes and simple string concatenation removed. Parameter aliases come from Microsoft Learn (`about_Pwsh` and `about_PowerShell_exe`), listed in `src/engine/library/parameters.ts`.

## Checks

- Every column written by the tool exists in the uploaded schema (a failure here means the output must not be used).
- Join key strength and type, and how many sampled keys find a match.
- Indicator matches in the sample.
- An evasion test bench of synthetic command lines, comparing the original and hardened conditions.
- Sample row counts matched by the original and hardened conditions.
- Names in the original rule that are not in any uploaded schema (approximate).

The checks use JavaScript approximations of KQL operators. They confirm field names and joins against your samples, not that the query runs, so always execute the output in the target workspace before deploying.

## Known limits of this build

- The KQL reader handles a single main query with let statements. Unions, nested queries and complex predicates (with `or` or functions) are left unchanged and flagged.
- Enrichment is inserted before the first shaping operator (`project`, `summarize` and similar). If that is a `summarize`, the added columns need adding to it by hand; a warning says so.
- Prefix expansion for PowerShell parameters follows PowerShell's prefix matching behaviour, which is not documented parameter by parameter. Confirm it in the lab.
- Base64 payload decoding is not applied yet.
- Exports target Sentinel analytics rule YAML; Defender custom detection rules are not exported yet.

## Project layout

```
src/engine/            Rules engine (no DOM, unit tested)
  kql.ts               Tokeniser and structure reader

  library/             Command-line parameter library
```
